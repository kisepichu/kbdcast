# 015 or-pattern

- 状態: open
- Emela: v0.28.2
- 意図: regex の parser（`regex/src/syntax.emel`）で、同じ扱いをする複数のパターンを match の 1 つの腕で受ける。`*`、`+`、`?` はどれも「nothing to repeat」、`(?=` と `(?!` はどちらも「lookahead is not supported」、など
- こう書きたかった:
  `wish/syntax.emel` の 7 か所（`:97`、`:114`、`:120`、`:206`、`:208`、`:220`、`:276`）。`|` で並べる（Rust、OCaml、Gleam の or-pattern）
  ```emela
  (Some('*'), _) | (Some('+'), _) | (Some('?'), _) ->
    raise RegexSyntax(message: "nothing to repeat", offset: s.pos)
  ```
  regex の program（`regex/src/program.emel`、計画の Task 6。wish-first の単位でないので wish は無い）でも、AST の葉の 4 つ（`Literal`、`Dot`、`Class`、`Assert`）を 1 つの腕で受けたかった: `size` の `Literal(_) | Dot | Class(..) | Assert(_) -> 1`、`groups` の `... -> []`、`can_be_empty` の `Literal(_) | Dot | Class(..) -> False`
  regex の差分テストの生成器（`wish/pattern_gen.emel:114`、計画の Task 8）でも、量指定子をそのまま続けてよい AST の節（文字、class、group など）を 1 つの腕で受けたかった: `Literal(_) | Dot | Class(_, _) | Capture(_, _) | NonCapture(_) -> t; _ -> "(?:" ++ t ++ ")"`
  key codec の型（`wish/key.emel:49`、サブプロジェクト 2 の計画の Task 2）でも、同じ代表（`Backspace`）になる制御文字 0x08 と 0x7F を `0x08 | 0x7F -> (Backspace, NO_MODS)` と 1 つの腕にした
  key codec の表記（`wish/notation.emel:86`、`:99`、サブプロジェクト 2 の計画の Task 3）でも、同じ修飾の 2 つの名前を `'m' | 'a' => Some(Alt)` と、同じキーの 3 つの名前を `"cr" | "enter" | "return" => Some(Enter)` と 1 つの腕にした
  key codec の decode（`wish/decode.emel:98-100`、`:144`、`:157`、`:168`、サブプロジェクト 2 の計画の Task 4）でも、CSI の終わりの文字を `'A' | 'B' | 'C' | 'D' | 'H' | 'F'` と `'P' | 'Q' | 'R' | 'S'` に、F11 と F12 の番号を `23 | 24 -> Some(Function(f_key(n - 12)?))` に、Backspace になる 2 つの番号を `127 | 8 -> Backspace` に、それぞれ 1 つの腕にした
  key codec の encode（`wish/encode.emel:99`、`:102-107`、サブプロジェクト 2 の計画の Task 6）でも、termwiz の `ctrl_mapping` を写して、同じ制御文字になる文字を `'@' | '`' | ' ' | '2' -> Some(0x00)`、`'[' | '3' | '{' -> Some(0x1b)` など 7 つの腕にした
  VT の parser（`wish/parser.emel:70-113`、サブプロジェクト 3 の計画の Task 3）でも、avt 0.18.0 の `Parser::feed` の 1 つの match を写し、同じ遷移をする状態（`(CsiParam | CsiEntry | CsiIntermediate, 0x40..=0x7e)`、C0 を実行する 6 つの状態の `(Escape | EscapeIntermediate | CsiEntry | CsiParam | CsiIntermediate | CsiIgnore, ...)`）、文字（`(_, 0x18 | 0x1a | 0x80..=0x8f | 0x91..=0x97 | 0x99 | 0x9a)`、`(Escape, 0x58 | 0x5e | 0x5f)`）、組そのもの（`(CsiParam, 0x3c..=0x3f) | (CsiIntermediate, 0x30..=0x3f) | (CsiEntry, 0x3a)`）を、それぞれ 1 つの腕にした（`:74`、`:76-77`、`:80-81`、`:84`、`:86`、`:90`、`:92`、`:94`、`:96-98`、`:101`、`:103-107`）。範囲パターン（038）と組み合わせている
  VT の解釈（`wish/terminal.emel`、サブプロジェクト 3 の計画の Task 5）でも、avt の dispatch で同じ操作になる CSI の終わりの文字の 4 組（`(None, 'B') | (None, 'e')`、`(None, 'C') | (None, 'a')`、`(None, 'G') | (None, '`')`、`(None, 'H') | (None, 'f')`。`:84-85`、`:89-90`）、LF と同じ動きをする 4 つの制御文字（`0x0A | 0x0B | 0x0C | 0x84 => linefeed(t)`。`:180`）、SGR の 21 と 22（`[[21], ..rest] | [[22], ..rest]`。`:203`）、38 の 2 つの RGB の書き方（`[[38, 2, r, g, b], ..rest] | [[38, 2, _, r, g, b], ..rest]`。`:210`）、modifyOtherKeys の n を省いたときと 0（`None | Some(0) => Some(Off)`。`:147`）を、それぞれ 1 つの腕にした
- 診断:
  wish check（v0.28.2）では char literal の E0105（013）と混ざって読めなかった。wish の `:97` の `None | Some('|') | Some(')') -> ...` には、match の腕なのに ``error[E0317]: refutable pattern in binding: pattern `None` not covered``（``= help: use `match` to handle the other cases``）が出た
  repo の外の使い捨ての Pome で、char literal を使わずに書いた最小の形（`c match {` の腕 `STAR | PLUS -> 1` と `_ -> 0`。`STAR` と `PLUS` は Int の const、2026-11-25）で 6 つ: ``E0110: expected `->` ``（最初の `|` を指す）、``E0110: expected `|` ``、E0118、``E0122: expected newline or `}` after match arm``、``E0301: type mismatch: expected `Int`, found `fn(Int) -> {unknown}` ``、``E0317: refutable pattern in binding: pattern `_` not covered``。`| PLUS -> 1` を anonymous function と読んでいる。どれも「or-pattern は無い」とは言わない
  program（Task 6）では or-pattern を書かなかった（このメモで無いと分かっていた）ので、診断は無い
  差分テストの生成器（Task 8）の wish では、同じ行の `let`（004）の E0118 と E0122 に埋もれ、or-pattern には届かなかった
  key の wish（Task 2）では、`=` で書いた関数の本体（020）の中にあり、読まれなかった
  表記の wish（Task 3）では、`:99` に ``error[E0301]: type mismatch: expected `Option[KeyCode]`, found `fn(String) -> String` `` と ``error[E0317]: refutable pattern in binding: pattern `_` not covered``（`| "enter" | "return" => ...` を anonymous function と読んでいる）。`:86` は char literal の E0105（013）と混ざった
  decode の wish（Task 4）では、`:157` と `:168` に、表記と同じく ``E0110: expected `->` ``、``E0110: expected `|` ``、E0118、E0122、``E0301: type mismatch: expected `Option[KeyCode]`, found `fn(Int) -> {unknown}` ``（`:168` は `KeyCode`）、``E0317: refutable pattern in binding: pattern `_` not covered`` の 6 つずつ。`:98-100` と `:144` は char literal の E0105（013）と混ざった
  encode の wish（Task 6）では、7 つの腕のどれも char literal の E0105（013）と混ざった。`:102` と `:107` の腕には、`|` の後ろを読んだ ``E0301: type mismatch: expected `Option[Int]`, found `List[?0]` ``（`'['` の中身）と ``E0301: type mismatch: expected `Option[Int]`, found `Int` `` が出た
  VT の parser の wish（Task 3）では、組のパターンの中の状態の or-pattern（`:74`、`:92`、`:96`、`:104`）に、最初の `|` を指す ``E0112: a tuple pattern needs at least two elements``、``E0110: expected `)` ``、``E0110: expected `->` ``、E0122 と、`| CsiEntry | ...` を anonymous function と読んだ ``E0301: type mismatch: expected `(Parser, Step)`, found `fn(State) -> State` `` と ``E0317: refutable pattern in binding: patterns `Ground`, `Escape`, `EscapeIntermediate` and 10 more not covered``。文字の or-pattern（`:90`、`:106`、`:107`）には、`|` を指す E0110 が 2 つ、E0122、``E0301: ... found `fn(Int) -> Int` `` と ``E0317: refutable pattern in binding: pattern `_` not covered``。行の頭の、組どうしの `|`（`:81`）には ``E0113: expected pattern`` と ``E0301: ... found `(State, Int)` ``。どれも「or-pattern は無い」とは言わない。腕は `=>` で書いていたので、``expected `->` `` はその誤りとも重なる
  VT の解釈の wish（Task 5）では、CSI の 4 組（`:84-85`、`:89-90`）は char literal の E0105（013）と混ざった。`:180` には、parser の文字の or-pattern と同じく、最初の `|` を指す ``E0110: expected `->` ``、E0122、`| 0x0B | ...` を anonymous function と読んだ ``E0301: type mismatch: expected `Terminal`, found `fn(Int) -> Int` `` と ``E0317: refutable pattern in binding: pattern `_` not covered`` の 4 つ。`:203` と `:210` には 6 つずつ: ``E0110: expected `->` ``、``E0110: expected `|` ``、E0118、E0122、``E0301: type mismatch: expected `Terminal`, found `fn(List[List[Int]]) -> {unknown}` ``、``E0317: refutable pattern in binding: patterns `[[_], ..]`, `[[], ..]`, `[[_, _, ..], ..]` and 1 more not covered``（`:210` は `[[38, _, _, _, _, _], ..]` などで `and 7 more`）。`:147` は `let`（004）の行の前置の match の中にあり、届かなかった。どれも「or-pattern は無い」とは言わない
- 回避策:
  `||` の guard にした（`[c, ..] if c == ASTERISK || c == PLUS || c == QUESTION -> ...`）。腕の終わりの判定（wish の `:97`）は guard を裏返し、`[c, ..] if c != BAR && c != CLOSE_PAREN -> 続ける`、`_ -> 終わる` にした。印は `regex/src/syntax.emel` の 7 か所の `FRICTION(015)`
  program（Task 6）: 葉の腕を 1 つずつ書いた（`size` と `groups` に 4 つずつ、`can_be_empty` に 3 つと `Assert(_) -> True`。3 か所の `FRICTION(015)`）。`_` の腕にまとめれば 1 行で済むが、Node に構成子が増えたとき compiler が抜けを教えなくなる（命令の数を数える `size` と、実際に命令を作る `code` がずれると、展開の上限が正しく効かない）ので、網羅性を残す形にした
  差分テストの生成器（Task 8、`regex/test/pattern_gen.emel` の `write`）: 量指定子を直に付けてよい節の 3 つ（`Atom(_)`、`Group(..)`、`NonCapture(_)`）を、同じ `text` を返す 3 つの腕にし、残りを `_ -> "(?:#{text})"` にした（`FRICTION(015)` の印 1 か所）
  key（Task 2、`src/key.emel` の `representative`）: 0x7F を別の腕にし、0x08 の腕と同じ値を返す（`FRICTION(015)` の印 1 か所）
  表記（Task 3、`src/key/notation.emel` の `modifier` と `named`）: `A-` の腕と、`enter`、`return` の腕を別に書き、同じ値を返す（`FRICTION(015)` の印 2 か所）。どれも literal と const のパターンなので網羅性の判定には数えられるが、同じ値を返す腕が並ぶ
  decode（Task 4、`src/key/decode.emel` の `tilde` と `letter`）: 23 と 24 の腕と、`P`、`Q`、`R`、`S` の 4 つの腕を別に書き、それぞれに F の番号を書いた（`FRICTION(015)` の印 2 か所）。`A` から `F` の 6 つは、CSI の終わりの文字を `_` の腕で受け、`cursor(f)` が `None` を返せば読めない列になる形にしたので、or-pattern は要らなかった。`127 | 8` も、`Key.key` が制御文字を代表にする（8 と 127 は `Backspace`）ので `Char(c)` のまま渡し、腕ごと無くなった
  encode（Task 6、`src/key/encode.emel` の `ctrl_mapping`、`FRICTION(015)` の印 1 か所）: 英字と記号は、`@` から `~` の 1 つの guard（低い 5 bit が制御文字になる、038）にまとめたので、or-pattern が要るのは、同じ制御文字になる空白と `2`、`7` と `/`、`8` と `?` の 3 組だけになった。それぞれ別の腕に書き、同じ値を返す
  VT の parser（Task 3、`src/vt/parser.emel` の `feed`、`FRICTION(015)` の印 1 か所）: avt の 1 つの match を、どの状態でも同じ遷移をする文字（ESC、CAN、SUB と C1）の腕と、状態ごとの match に分け、状態の中では文字の範囲を順に並べた guard にした（038）。同じ遷移をする状態の組は、状態ごとに同じ腕を書いた（C0 を実行する `_ if k < 0x20 -> (p, Emit(Execute(c)))` が 6 つ、DEL を捨てる `DEL -> (p, Nothing)` が 8 つ、CSI を終える腕が 3 つ、ESC を終える腕が 2 つ）。SOS、PM、APC（C1 の 0x98、0x9E、0x9F と、ESC の後の `X`、`^`、`_`）も 1 つずつ腕を書き、同じ値を返す。CAN、SUB と残りの C1 は、`_ if k == CAN || k == SUB || k >= 0x80` の guard にした
  VT の解釈（Task 5、`src/vt/terminal.emel`、`FRICTION(015)` の印 5 か所）: 同じ操作になるものは、それぞれ別の腕に書き、同じ値を返す（`csi` の `B` と `e`、`C` と `a`、`G` と `` ` ``、`H` と `f`、`execute` の LF、VT、FF、IND、`dec_mode` の 47 と 1047 の set と reset、`sgr` の 21 と 22）。38 と 48 の色は `sgr` から `extended` に分け、1 つの引数の中の RGB の 2 つの書き方を 2 つの腕にした（`extended` の印）。47 と 1047 は wish に書かなかった所で、avt の `dec_mode` が 2 つの番号を同じ mode にしている。modifyOtherKeys の `None | Some(0)` は、n を省いたときを 0 と読む `arg`（avt が持たない引数を 0 と読むのと同じ）で読むので、腕ごと要らなくなった
- コスト:
  行数はほぼ同じ。guard の腕は網羅性の判定に数えられず、下の腕を覆うかどうかも見られない（`[fn.match]`）ので、腕の重なりと抜けを compiler が調べない。長い `||` の guard は `emela fmt` が壊す（019）。普段のコードに基盤レベルは漏れていない。program では 3 つの match に、or-pattern なら 1 行の所が 4 行（`can_be_empty` は 3 行）。key では 1 行の所が 2 行。表記では 1 行の所が 2 行と 3 行。decode では 1 行の所が 2 行と 4 行
  encode では、or-pattern なら 3 行の所が 6 行
  VT の parser では、行数は avt の match（`parser.rs:420-627`、約 210 行）より少ない（状態ごとの match で約 90 行）が、avt の表の 1 つの腕が状態の数だけの腕に分かれ、avt の表と 1 つずつ見比べられない（どの状態のどの文字の腕かを引き直す必要がある）。guard の順に頼るので、腕を並べ替えると意味が変わり、重なりも抜けも compiler が調べない。avt と同じ遷移かは、avt の `feed` をそのまま写した使い捨ての Rust と、ランダムな入力（2 万 9 千ほど）で action の列を比べて確かめた
  VT の解釈では、or-pattern なら 1 行の所が、CSI の 4 組と SGR の 21 と 22 と RGB の 2 つの書き方で 2 行ずつ、LF の 4 つで 4 行、47 と 1047 で 4 行（set と reset）。avt の `csi_dispatch` と `execute` も、この終わりの文字と制御文字を別の腕に書いている（`(None, 'C')` と `(None, 'a')` が同じ `Cuf` を返す）ので、avt と 1 つずつ見比べるのには困らない。avt の SGR の decoder は or-pattern（`[21] | [22]`、`[38, 2, r, g, b] | [38, 2, _, r, g, b]`）で、ここは avt より腕が増えた
